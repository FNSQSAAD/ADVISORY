# Finance Square chatbot

An embedded assistant on every page of fnsq.com.au. It answers questions about
the firm and about Australian mortgages, runs the site's calculators
conversationally, captures qualified leads into GoHighLevel, and books the
15-minute strategy call.

It contains **no LLM**. Every answer comes from a fixed knowledge base or from
arithmetic, so it is fully reproducible, testable, costs nothing per message,
and cannot invent a rate, a fee or an approval. That is the right trade for a
credit-licensed business.

---

## Files

| File | What it is |
|---|---|
| `api/chat.js` | HTTP endpoint. Rate limit, lead POST, response shaping. |
| `api/_engine.js` | The brain: intent router, calculators, lead state machine. |
| `api/_retrieve.js` | BM25 retrieval **and the rules for refusing to answer**. |
| `api/_tokens.js` | Tokeniser shared by the index builder and the retriever. |
| `api/_slots.js` | Pulls money, rates, terms, states, emails and mobiles out of free text. |
| `api/_kb.json` | Built artefact: 189 passages + precomputed BM25 index. |
| `js/finance-core.js` | **Generated.** DOM-free copy of the calculator maths. |
| `js/chat.js` | The widget. |
| `css/chat.css` | Widget styling, standalone like `css/footer.css`. |
| `tools/*` | Build and test scripts (below). |

Files in `api/` starting with `_` are not routed as functions by Vercel.

## Build and test

```bash
node tools/extract-site.js     # site HTML  -> tools/kb-site.json
node tools/build-kb.js         # + kb-faq.js -> api/_kb.json
node tools/build-finance-core.js   # calculators.js -> js/finance-core.js
node tools/parity-test.js      # 3,867 checks: finance-core == calculators page
node tools/test-engine.js      # 113 checks: answers, refusals, calcs, lead flow
node tools/apply-chat.js       # inject the widget into every .html (idempotent)
node serve.js                  # localhost:8830, runs the /api functions in-process
node tools/e2e-lead.js <base> [--dry]   # drive a full lead conversation
```

Run `parity-test.js` and `test-engine.js` before any deploy. Re-run
`build-finance-core.js` + `parity-test.js` after **any** edit to
`js/calculators.js`.

## Design decisions worth keeping

**The maths is not reimplemented.** `js/finance-core.js` is generated by lifting
the DOM-free functions out of `js/calculators.js` verbatim, and
`tools/parity-test.js` evaluates both copies across 3,867 inputs to prove they
agree. A figure quoted in chat is therefore the same figure the calculators page
produces. Reimplementing the maths would have let the two drift, and a broker
site that quotes two different stamp duties for the same house has a real
problem.

**Refusing is a feature.** `api/_retrieve.js` `answer()` returns null unless
three gates pass, and the bot then says it does not know and offers the call.
The gates exist because each one caught a real wrong answer during testing:

1. A one-word match must be a *headline* word of that entry. "Can you write me a
   poem" matched the free-service FAQ on "writing", which appears once in its
   answer prose.
2. A question of three or more meaningful words must land at least two of them.
   "Who won the grand final" matched "final".
3. Absolute score and coverage floors.

Stopwords are stripped **before and after** stemming, or "whats" survives the
first pass, stems to "what", and matches every page whose heading is a question.

**A calculator trigger with no numbers in it defers to the knowledge base.**
"What is LMI" and "do credit cards affect borrowing power" want an explanation;
"what LMI on a $780k place with $60k down" wants the tool. Entries that exist
only to launch a calculator are tagged `topic: 'calculator'` and fall through.

**Slot assignment is range-checked.** "I earn 95k and my partner earns 70k with
2500 a month expenses" put the partner's salary into the expenses slot until
each slot got a plausible magnitude, which collapsed the estimate to "the
numbers look tight". Amounts under $1,000 with no unit or dollar sign are
"weak": a labelled match may use them ("an extra 400 a month"), positional
fill may not.

## The GoHighLevel path

```
widget -> POST /api/chat -> engine
                             |  (only after explicit consent)
                             v
                      POST /api/lead  (this site's existing relay)
                             |
                             v
    GHL inbound webhook afa2d705-3d71-495d-81c7-88b8f7167b29
                             |
       Website Form Receiver -> New Lead Intake -> Follow-Up Ladder
```

There is deliberately **no second capture path**. `/api/lead` already normalises
`timing` and `goal` into the exact spellings GHL's RADIO fields accept, so the
chatbot sends those spellings (`GOALS[].goal` and `TIMINGS[].timing` in
`_engine.js` must stay in sync with the `GOAL`/`TIMING` maps in `api/lead.js`).

Booking uses the existing live GHL calendar widget
`api.leadconnectorhq.com/widget/booking/jjntJeKyOuid8eFZkm7W` in an iframe, so
slots, confirmations and the appointment workflows are GHL's own. The iframe is
only created when a booking block is rendered, so it never loads for a visitor
who does not ask to book.

Nothing is sent to GHL until the visitor answers the consent question with a
clear yes. Answering "no" discards the details and says so. If the POST fails,
the bot says it failed and offers the phone number, rather than showing a
success message for a lead that does not exist.

### The ghost-contact trap (important)

The GHL attribution script (`link.msgsndr.com/js/external-tracking.js`) runs on
every page and **creates a CRM contact from any form submission it observes**.
The first version of this widget used a `<form>` for the message input, and
every chat message produced an empty `external_form` contact that then ran the
whole New Lead Intake workflow, complete with tags, consent stamp and broker
alert, for a lead with nobody in it. Four appeared in production within four
minutes of local testing.

The input is therefore a `<div>`, the send button is `type="button"`, and the
textarea has no `name`. **Do not turn `.fq-form` back into a `<form>`.**
(This is the same class of bug as the `contact.html` ghost fixed on 2026-09-08.)

## Compliance

`COMPLIANCE` in `_engine.js` is attached to **every** response and rendered two
ways: a permanently visible footer strip inside the panel carrying the licence
and the free-service line, and a per-message "Important information" control
that reveals all three. Messages containing figures are flagged `estimate: true`
and their control reads "Estimates only, important information".

The bot will not give credit advice, will not quote a rate, and will not say
anyone is approved. `tools/test-engine.js` asserts all of this, including
against prompt-injection style input.

Anything that changes yearly - duty thresholds, scheme caps, tax scales - is
described by mechanism in the FAQ layer rather than by a number that will rot.
The exception is the stamp duty calculator, which uses the site's own verified
scales and always prints the "confirm with the state revenue office" note.

## Updating the knowledge base

Edit `tools/kb-faq.js`, then `node tools/build-kb.js`. Add the phrasings people
actually type to `alt`: they feed both the index and the exact-match shortcut,
which is what rescues short queries like "what loan should i get" that BM25
cannot score. After editing site copy, re-run `extract-site.js` too.
